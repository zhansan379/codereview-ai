# aacr-bench 全量评测报告：codereview-ai vs OCR vs Claude Code

同一模型（`deepseek-v4.1-flash`）、同一数据集（aacr-bench 全量 196 条真实 PR，50 个仓库、10 种语言、1506 条人工标注的参考评论）、同一判官下，三家各自跑一遍全量。

**一句话结论**：三家的语义 F1 都在 0.16–0.18、行号 F1 都在 0.32–0.35 这个窄带里，没有数量级差距。
**codereview-ai 的位置最准**（行号精确率 0.523，三家最高），但**报得最少、覆盖面最窄**（语义召回 0.115，三家最低）；
OCR 两项 F1 都最高、最均衡；Claude Code 报得最多、召回最高，代价是精确率垫底。

## 2. 各项指标怎么解读

**先记住两条口径**，否则数字会看反：

- **精确率的分母是「自己报了多少条」**。报得越多，分母越大，越容易被自己的多报拉低。
- **语义召回不可能高于行号召回**。评测是「先看位置对不对，位置对了再问判官这两条说的是不是同一件事」，所以位置没对上就自动算漏。

### 2.1 行号精确率：codereview-ai 明显领先（0.523 vs 0.489 vs 0.362）

含义是「报出来的问题里，一半以上能落在人工标注的那一行（±1 行内）」。

**codereview-ai 领先的原因**：它报得最少（648 条），但每条都被要求锚定到 diff 的具体改动行上才输出，天然不容易飘。
换句话说，**这是「少报 + 每条都定位准」换来的高精确率**，不是「找得比别家多」。

Claude 的 0.362 最低，直接原因是它报了 1128 条，其中大量是「位置沾边但关注点不同」的评论——分母被撑大了。

### 2.2 语义召回：三家都低（0.115 / 0.138 / 0.157），这是数据集难度

召回低不代表工具差。拆开看漏在哪（详见 §4）：

- **一半左右的参考评论，三家在同一个文件上一条评论都没报**（「压根没看到」）；
- 另外三成是「看到了、位置也差不多，但行号没卡在标注的那几行上」。

也就是说，**漏报的大头是模型没覆盖到，不是行号算法或判官的锅**。剩下的一半则是位置锚定问题。

### 2.3 生成数 vs 精确率：Claude 的「多报换召回」

Claude 报了 1128 条，是 codereview-ai 的 1.74 倍。多出来的部分绝大多数**没有对应的参考标注**——不代表报错了，而是**参考集本身只标注了一部分问题**。

结果就是：Claude 的召回最高（0.157，报得多自然更容易碰到真问题），但精确率最低（0.197）。这是它历次评测一贯的表现。

**对生产意味着什么**：如果下游是人工逐条看评论，多报就是负担；如果是拿来当「不漏」的安全网，Claude 的取向更合适。codereview-ai 反过来——安静、位置准，但容易漏。

### 2.4 语义 F1：OCR 略胜（0.178），但差距不大

OCR 生成数居中（781），召回（0.138）和行号精确率（0.489）都不差，没有明显短板，所以两个 F1 都是第一。三家的 F1 差距（0.158–0.178）在单样本 ±1 条 finding 的波动范围内，**不宜据此断言谁显著更强**。

## 3. 分语言看：谁强谁弱

下表是各语言的**语义召回**（命中/参考），括号里是三家生成数：

| 语言 | 实例 | codereview-ai | OCR | Claude |
|---|---|---|---|---|
| C++ | 33 | 0.106 | 0.124 | 0.110 |
| Java | 30 | 0.119 | 0.137 | **0.196** |
| TS | 29 | 0.108 | **0.148** | 0.141 |
| Go | 22 | **0.167** | 0.144 | 0.161 |
| Python | 21 | 0.155 | 0.165 | **0.214** |
| C | 19 | 0.108 | **0.158** | 0.137 |
| JS | 11 | **0.056** | **0.130** | 0.093 |
| PHP | 11 | 0.049 | 0.049 | **0.293** |
| C# | 10 | 0.133 | 0.133 | **0.289** |
| Rust | 10 | 0.106 | 0.128 | **0.234** |

**值得注意的三点**

1. **JS 是 codereview-ai 的明显短板**：召回 0.056，不到 OCR（0.130）的一半，而且它在 JS 上只生成 27 条（另两家 62/61 条）——是**没覆盖到**，不是「报了没中」。这是最值得查的方向。
2. **PHP 上 codereview-ai 和 OCR 几乎放弃**（都是 0.049，OCR 只生成 8 条），Claude 却做到 0.293。
3. **C++ 是最大分层（33 实例 / 283 条参考），三家都在 0.106–0.124**——这是全体共同的天花板，跟工具无关，更像模型在这类代码上的普遍难点。

Claude 在 C# / Rust / Java / PHP 上领先，但同一批语言的生成数也是三家里最多的——**优势仍然来自「多报」**，不是定位更准。

## 4. 漏报归因：漏在哪，为什么

把三家没命中的参考评论归类（同一套规则，明细可查）：

| 类别 | codereview-ai | OCR | Claude |
|---|---|---|---|
| ① 模型没看出来（同文件一条评论都没有） | 660（53%） | 619（51%） | 532（45%） |
| ② 看到了但行号没锚准 | 394（31%） | 390（32%） | 440（37%） |
| ③ 判官认为「不是同一个问题」 | 197（16%） | 209（17%） | 219（18%） |
| （另计）多报：报了但没对上任何参考 | 486 | 584 | **906** |

**结论**

- **最大漏报来源是「没看到」，占一半**——想提升召回，优先做「让模型覆盖更多文件/更多位置」，而不是调行号。
- **行号锚定问题占三成**，其中一部分是评测框架的结构性限制：一条生成评论只能贡献一次行号命中，相邻多行的参考没法被一条评论同时记中（这部分不是产品问题）。
- **判官判否占 16–18%**：位置对了但判官认为关注点不同，这部分与判官口径强相关，换判官数字会变，解读时要留余地。
- Claude 的多报量（906）是另两家的 1.5–1.9 倍，这是它精确率最低的直接原因。

## 5. 成本

| | codereview-ai | OCR | Claude Code |
|---|---|---|---|
| 输入 token | **135.6M** | 335.1M | 405.5M |
| 其中缓存读 | 未上报 | 295M（88%） | 398.1M（98.2%） |
| 输出 token | 5.9M | 12.3M | 6.8M |
| 单条平均耗时 | **276s** | 546s | 284s |
| 单条平均输入 | 737k | 1821k | 2204k |

- **codereview-ai 最省**：token 约为 OCR 的 41%、Claude 的 34%，单条耗时也是最短的。
- **OCR 又贵又慢**：token 是 codereview-ai 的 2.5 倍，单条耗时是它的 2 倍。**这不是个别样本造成的**——单条输入中位数
  OCR 898k vs codereview-ai 484k（1.9 倍），中位数就已经翻倍；重样本上差距更大（如 `microsoft/typescript-go` 那条：
  OCR 17.4M vs codereview-ai 1.3M）。原因是 OCR 的工作方式「选文件 → 逐个探索」：单条平均审 8.3 个文件、
  89 次工具调用（最多 212 文件 / 702 次调用），每一轮都要把累积上下文重发，token 随「轮数 × 上下文」增长；
  而 codereview-ai 只围绕 diff 改动行做锚定，探索面小得多。耗时同理——轮数是串行的模型调用。
  代价换来的产出并不更多：OCR 单条产出评论中位数 3 条，与另两家相当。
- **缓存口径**：网关本身会自动缓存（实测同一前缀第二次调用 97.8% 命中）。OCR / Claude 都上报了缓存拆分，
  **codereview-ai 只上报总输入、未拆分缓存**，所以三家的原始 input 数字不能当作「新鲜输入」直接比价。

## 6. 实验环境（简要）

- 三家评审器都通过 **opencode go 网关**调用同一个模型 `deepseek-v4.1-flash`；三家各用独立仓库目录并行跑，均为**生产默认配置**（codereview-ai 的 review_filter、OCR 的 post-filter 都开着）。
- 语义判定用 `deepseek-v4.1-flash` 当判官（temperature=0）。判官与三家被测模型同源，**可能对同款模型有轻微偏好**，这是本轮的已知局限。
- 全量 196 条、每条约 276–546 秒，评审阶段实际跨约 21 小时（含失败重试）。
- 12 条缺失是数据集缺陷（上游 commit 已删除 11 条 + 1 条仓库路径在 Windows 上非法），三家一致，不影响横向对比；
  逐条清单与数据集来源见 [未纳入评测的 15 条样本说明](./benchmark_aacr_bench_excluded.md)。

## 7. 结论与建议

1. **三家在同一档位**，选型应看取向而不是看 F1 小数点：要**位置准、评论少而精**选 codereview-ai；要**尽量不漏**选 Claude Code；要**均衡**选 OCR。
2. **提升召回的最优先方向是覆盖面**（一半漏报是「同文件一条都没报」），而不是行号定位。
3. **codereview-ai 的 JS 覆盖值得单独排查**（只生成 27 条，召回 0.056，明显低于另两家）；PHP 上几乎没输出，也值得确认是有意过滤还是漏了。
4. 单样本有 ±1 条 finding 的波动，**要比较版本改进，建议同一批样本重复跑 3 次以上**再下结论。
